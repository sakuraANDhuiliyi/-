## 结论

**后续更新：用户重新登录后搜索已恢复。** 本地日志确认，北京时间 18:47:51 至 18:52:23，连续 7 次 `searchProductByAgent` 同时返回 HTTP 200 和业务码 200，见 [恢复后的响应元数据](403-recovery-observations.json)。该时间窗口的恢复已经得到验证，尚不能据此保证登录态长期不再变化。

此前同一运行环境中，Passport 校验及地址解析正常，商品搜索接口返回带拦截响应头的 HTTP 403 HTML 页面；第一页、没有分页游标的请求也失败，按上游请求头发送的对照请求同样失败。

新的证据使授权凭证/会话状态成为优先排查方向：Passport 接受某个 Token，不保证搜索业务当前也接受它。重新授权可以恢复本次问题，但重新登录也伴随时间推移，尚未严格隔离服务端策略恢复等因素，不能把所有 403 都认定为 Token 过期。

## 已修正和补充

1. 业务请求头与上游对齐：不再统一附加 Passport 的 Accept/User-Agent；Passport 请求继续显式附带自己的请求头。
2. 修正潜在分页问题：不再悄悄截断超过 300 字符的 `queryId`、`requestId`。2048 字符以内完整传递，超长时明确报错。没有证据表明第一次失败的游标实际超过 300 字符，因此这不是已证实的 403 根因。
3. 增加本机安全诊断：`.runtime/upstream.jsonl` 只记录时间、方法、URL 路径、状态码、耗时、响应类型/大小、业务码、拦截头是否存在和时钟偏差。日志不记录查询字符串、请求体、用户 Token、签名或响应正文，大小超过约 256KB 时截断；不进入 Git。
4. 403 不自动重试，也不当作 Token 过期清除登录；网页保留已加载商品，并将登录状态说明改为“查询暂不可用”。
5. 登出操作不再错误地把美团服务状态标为刚刚连接成功。
6. 根据恢复证据补充“重新扫码授权”入口：搜索返回 403 后可直接发起新的授权，不必先退出。用户扫码成功后才替换凭证；取消时保留原凭证。重新授权完成会清除旧搜索错误和旧分页游标，要求重新搜索后再翻页，不自动重放失败请求。

14 项自动检查通过，覆盖：UTF-8 请求体签名切片、原业务请求头、认证专用请求头、诊断不包含敏感值、长游标不被截断、403 不重试，以及重新授权成功/取消时的凭证替换行为。
